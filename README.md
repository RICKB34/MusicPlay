# Rhythm Forge

选一首**本地音乐**，自动识别它的节奏与音色，生成一份可玩的 4/6 轨下落式音游谱面，
支持双人用同一份谱面实时对战。手机和电脑都能用（PWA）。

---

## 为什么是"本地音乐"而不是"正在播放的音乐"

这不是偷懒，是调研后的结论。三条硬约束：

1. **QQ音乐没有面向第三方的开发者接口。** 它的"开放平台"是音乐人内容平台
   （上传作品、分成），不是 API 平台。客户端也没有插件/扩展 SDK。
2. **抓正在播放的音频这条路物理上走不通。** `tabCapture` / `getDisplayMedia`
   对 DRM 内容会输出**静音**，拿不到可分析的 PCM；而且 iOS/Android 沙盒
   **禁止**捕获其他 App 或系统音频——手机端根本不可用。
3. **绕过加密是明确违法。** QQ音乐音频走 QMC 加密（`.mflac`/`.mgg`），
   解密触碰《著作权法》技术保护措施条款与《信息网络传播权保护条例》。

而分析**用户自己提供的音频文件**既绕开以上全部问题，又能用 `OfflineAudioContext`
做**全曲离线分析**——精度上限远高于实时流式分析。

代码里保留了 `AudioSource` 抽象接口（`src/types.ts`），将来若要接入别的音频来源，
只需新增一个适配器，核心分析管线不用改。

## 快速开始

**环境要求**：Node.js `^20.19.0 || >=22.12.0`（这是 Vite 8 的要求，开发环境用的是 v24）。

### 首次准备（只需做一次）

```bash
cd D:\code\HACKTHON_versions\HACKATHON(3)
npm install
```

### 日常启动

```bash
npm run dev
```

看到下面这样的输出就成功了：

```
  VITE v8.3.0  ready in 757 ms
  ➜  Local:   http://localhost:5173/
  ➜  Network: http://192.168.x.x:5173/
```

浏览器打开 **http://localhost:5173** 即可。

> **终端窗口要一直开着**，关掉服务就停了。

### 怎么打开终端

三种方式，挑顺手的：

1. **文件资源管理器**里进到 `D:\code\HACKTHON_versions\HACKATHON(3)`，在空白处**右键 → 在终端中打开**
   （最省事，会自动切到该目录，不用敲 `cd`）
2. **Win + X** → 终端
3. **Win + R** → 输入 `cmd` → 回车

### 怎么停止

在跑着服务的那个终端里按 **`Ctrl + C`**（可能要按两次）。

## 两种运行模式，用途不同

| 命令 | 地址 | 什么时候用 |
|---|---|---|
| `npm run dev` | `localhost:5173` | **平时开发、试玩**。改代码自动刷新，启动快 |
| `npm run build` + `npm run server` | `localhost:8787` | **参赛演示**。一个进程同时托管网页与对战服务 |

`build` 只需跑一次（改了代码才需重跑），之后每次演示就一条 `npm run server`。

**对战功能只在第二种模式下连得上**——前端默认连 8787 端口的对战服务。

### 部署到公网

推荐把网站与 WebSocket 对战服务作为一个 Node 服务部署。项目已提供
`render.yaml` 和完整步骤，直接看 [`docs/DEPLOY.md`](docs/DEPLOY.md)：

```bash
npm ci && npm run build
npm start
```

Render、Railway、Fly.io 等支持 Node 长连接的平台都可以使用这套命令。

## 手机上玩

### 三步走

1. **手机连上电脑所在的同一个 WiFi**
2. **看电脑终端输出里的 `Network` 那一行**，例如 `http://192.168.1.23:5173/`
3. **手机浏览器打开这个地址**

两种运行模式都支持（`5173` 或 `8787`，看你起的是哪个）。

### ⚠️ 找对 IP 地址（最容易卡住的一步）

终端会**列出多个 Network 地址**，因为它们对应不同的网络适配器：

```
➜  Network:  http://26.139.249.121:5173/   Radmin VPN        ← 手机连不上
➜  Network:  http://192.168.190.1:5173/    VMware Network…   ← 手机连不上
➜  Network:  http://10.31.196.164:5173/    WLAN              ← ★ 用这个
```

**只有标注 `WLAN` 或以太网的那个能用。** VPN 和虚拟网卡的地址手机是够不到的。

分不清的话，在终端跑 `ipconfig`，找「无线局域网适配器 WLAN」下面的 **IPv4 地址**。

### ⚠️ 连不上？九成是 Windows 防火墙

首次运行 `npm run dev` 时系统会弹一个安全警告，**必须勾选「专用网络」并点「允许访问」**。

如果当时点掉了，手动补：

> Windows 安全中心 → 防火墙和网络保护 → 允许应用通过防火墙 → 找到 Node.js，把「专用」勾上

### iOS 必读

| 事项 | 说明 |
|---|---|
| **必须先点一下屏幕** | 起始页的「点击开始」不能跳过。iOS 要求音频必须在用户手势里解锁，不点就没声音——**这不是 bug** |
| **横竖屏都行** | 布局自适应。4K 竖屏每轨占 25% 宽度，双手拇指够得着 |
| **添加到主屏幕** | Safari 分享菜单 → 添加到主屏幕，之后全屏无地址栏，像原生 App |
| **FLAC 可能解不了** | Safari 对 FLAC 支持不保证。遇到解码失败请把音频转成 MP3 |
| **切后台会停** | iOS 会挂起音频。回到页面后按提示点一下继续 |

### Android

Chrome 直接打开即可。「添加到主屏幕」会创建快捷方式。

### 手机上怎么操作

- **4K**：屏幕横向四等分，**用手指点对应的那一条**
- **6K**：六等分，同样点
- **支持多指同时按**——两个手指按两条不同的轨不会被吞掉

比键盘其实更好上手：轨道就是屏幕分区，所见即所点。

### ⚠️ 手机上一定要先做延迟校准

**触摸屏的输入延迟和桌面键盘完全不同**（手机通常 30-80ms，桌面 0-30ms），
再加上手机扬声器/蓝牙耳机的输出延迟，不校准的话判定会明显偏移。

在选曲页点「**延迟校准**」，跟着节拍声敲 16 次即可。
**戴蓝牙耳机的话这一步是必须的**——蓝牙延迟能到 100ms 以上。

### 手机上如果卡

低端安卓分析一首完整曲目可能耗时 8-15 秒。在选曲页把「分析精度」调到：

- **快** —— 计算量减半
- **演示** —— **只分析前 90 秒**，秒开，适合现场演示

### 关于离线

通过局域网 HTTP 访问时，**Service Worker 不会注册**（浏览器要求 HTTPS 才能用 SW），
所以没有离线缓存——但**联网状态下所有功能完全正常**。

想要完整的 PWA 离线体验，需要 HTTPS（自签证书或部署到线上）。

## 可能踩的坑

| 现象 | 原因与解决 |
|---|---|
| `'npm' 不是内部或外部命令` | Node.js 没装，或没装成功。去 nodejs.org 装 LTS 版 |
| 报找不到 `package.json` | 终端不在项目目录。先 `cd D:\code\HACKTHON_versions\HACKATHON(3)`，或用上面的右键方式打开终端 |
| 端口被占用 | Vite 会**自动顺延**到 5174、5175……看输出里的实际地址即可，不用管 |
| 手机打不开局域网地址 | ① 用错 IP（见上文「找对 IP 地址」）② Windows 防火墙拦了 Node |
| 手机上没声音 | 起始页没点「点击开始」。iOS 强制要求用户手势解锁音频 |
| 手机上判定总偏 | 没做延迟校准。触摸延迟和键盘差别很大 |
| 换手机就得重新校准 | 正常。校准值存在各设备本地，不同设备的延迟本来就不同 |

## 演示怎么最稳

**跑 `npm run build && npm run server`，两台设备连同一个 WiFi，
浏览器打开 `http://<局域网IP>:8787`。**

理由：对战服务器跑在本机，**RTT ≈ 0，网络风险归零**。这比连任何云端服务都可靠。

**选曲建议**：优先用**鼓点清晰的流行/电子乐**——节拍检测有明确的打击乐重音可依，
是最稳的选择。实测《卡农》这类无打击乐的弦乐合奏 BPM 检测也正常
（114.00 / 残差 11.6ms），所以古典并非禁区，但**样本只有 2 首，不足以打包票**。

真正会失效的是**自由节拍、无固定律动、极端变速**的素材。
遇到这类情况用调试页的手动 BPM 兜底。

**上台前请务必提前测一遍你要用的曲目**，别现场才第一次跑。

## 架构要点

### 1. 游戏循环与 React 完全隔离

`RhythmGame`（`src/core/engine.ts`）是一个普通 class，自己持有 rAF 循环和全部状态。
React 只负责创建它、销毁它。`GameScreen.tsx` 里**没有任何 setState 参与游戏循环**，
HUD 直接画在 canvas 上（DOM 文字更新会触发 layout，60fps 下是纯粹的浪费）。

### 2. 时钟：唯一主时钟是 `AudioContext.currentTime`

绝不用 `performance.now()` 或 rAF 时间戳做判定基准——rAF 有抖动（±4ms，掉帧时更多），
拿它判分会毁掉判定公平性：同样的手感，帧率高的设备拿高分。

```
songTime = ctx.currentTime − outputLatency − startCtxTime + userOffset
```

而且**判定是事件驱动的**：在输入回调里同步读时钟并立即判定，不等下一帧。
这样掉帧到 30fps 对判定精度的影响是零，只影响画面流畅度。

### 3. 谱面生成的核心理念：把听觉维度映射到视觉维度

没有可靠的音高信息（浏览器端复音音高提取做不准），凭什么让谱面"跟着音乐走"？

答案是用 **STFT 里免费拿得到的谱质心**（音色明暗）映射到轨道左右位置：

> 低沉的音（底鼓）→ 左侧轨；明亮的音（镲片）→ 右侧轨

这不是随机映射，而是**听觉维度到视觉维度的同构**。玩家听到底鼓时下意识知道音符在左边，
反复几次就形成"谱面在跟音乐"的强烈感知。此外还有重拍锚定外侧轨、反卡手、
左右手均衡、轨道冷却等约束做修正（`src/chartgen/lanes.ts`）。

### 4. 双人对战：共享时间轴 + 本地判定

服务器下发权威时间轴 `startAtServerMs`，双方各自用 NTP 式同步的时钟偏移
换算成本地 `AudioContext` 时刻，调 `source.start(when)`。

**判定完全在本地做，不跨网同步判定结果**——网络抖动绝不能影响手感。
只同步分数。这是音游对战的标准取舍，不做回滚网络码。

## 视觉主题（六套，可切换）

选曲页的「主题」卡片里切换。**实时生效、无需刷新**，选择存进 localStorage，
且**界面（DOM）与游戏画面（canvas）同步换**。

| 主题 | 风格 | 特征 |
|---|---|---|
| **QQ 音乐**（默认） | 简约 | 白底 + 品牌绿 `#31C27C` |
| 赛博 | Acid Graphics | 纯黑底 + 荧光绿/紫，直角硬阴影 + 扫描线 |
| 粘土拟态 | Claymorphism | 奶油粉底 + 超大圆角，内外阴影堆出 3D 立体感 |
| 霓虹复古 | Vaporwave | 深紫底 + 粉青双色霓虹重影 + 网格线 |
| 像素艺术 | Pixel Art | PICO-8 调色板 + 4px 粗边框 + 硬边偏移阴影，零圆角零过渡 |
| 水墨画风 | Ink Wash | 宣纸底 + 墨色字，细边框大留白，700ms 墨色晕染 |

**默认是 QQ 音乐风**——这个项目是给 QQ 音乐做的 demo。其余五套是可选风格。

### 怎么实现的

**一、组件规则只写一份，主题块只提供变量值**

`styles.css` 里所有组件规则（`.card` / `button` / `.seg` / `.theme-picker` …）
**只写一遍**，颜色、圆角、阴影、字体、动效曲线全部取自 CSS 自定义属性；每套主题
就是 `:root[data-theme='xxx']` 下的一个变量块（当前各 100 个）。加主题不动任何组件规则。

变量存的是**完整属性值**（整个 `box-shadow` 简写、整个 `border`），不是拆开的零件——
各主题的阴影**结构**根本不同（赛博是 `4px 4px 0 #a020f0` 零模糊单层，QQ 是柔和多层），
拆零件无法表达；而且 `box-shadow` 是逗号列表，其中一层为 `none` 时整条声明非法。

**二、canvas 与 CSS 各持一份调色板**

游戏画面由 canvas 绘制，读不到 CSS 变量。`getComputedStyle` 不是不能读，但
**绝不能放进渲染循环**（每帧强制样式重算，60fps 下是纯浪费）；改成启动时读一次
又有首屏时序陷阱，且**读不到时返回空字符串**，`ctx.fillStyle = ''` 会被静默忽略、
沿用上一帧颜色。

所以 `src/core/render.ts` 里每套主题各有一个 `RenderTheme` 对象，与 `styles.css`
的主题块手工配对，两边互加了交叉引用注释。实际重复量不大：CSS 侧只需要其中 6 个字段，
反过来 canvas 也完全不需要 `--card-shadow` / `--btn-*`。

**三、有一道测试守着变量契约**

CSS 变量取不到值时是**静默失败**的：`border: var(--x)` 退化成无边框、
`background: var(--x)` 变透明——编译器和控制台都不报任何错，只有切到那套主题的
肉眼看得到。

`src/state/theme.test.ts` 直接读 `styles.css` 源码，断言**每套主题的变量名集合与
`:root` 完全相等**，并断言每套主题在 CSS 里都有对应去处。加主题时漏定义变量，
这条测试会在提交前拦住。

### 加一套新主题要动三处

1. `src/state/theme.ts` —— 注册键 + 名称 + 一句话说明 + 色卡三色 + 状态栏色
2. `src/core/render.ts` —— `RenderTheme` 对象（canvas 那半边）
3. `src/styles.css` —— `:root[data-theme='新键']` 变量块

选择器 UI 和上面那道契约测试会自动跟随，不用改。

## 调试工具（选曲页 → 「调试工具」按钮）

**这是全项目 ROI 最高的组件。** 它把波形、节拍网格线、检测到的起音、生成的谱面、
量化残差全部叠在同一条时间轴上，播放头与音频严格同步。

验证因此变成一件直觉的事：**按下播放，耳朵听到底鼓的瞬间，
眼睛看到播放头正好压在小节线上**——BPM 和相位对不对，3 秒就能判断。

它同时是"分析失败"的最后一道保险：给两个滑块手动拖 BPM 和相位，
让网格线压住鼓点即可，永远有效。

## 验证方式

```bash
npm test
npm run typecheck
```

测试覆盖的是**产品设计假设**而非"代码跑不跑得通"：

- `src/chartgen/generate.test.ts` — 谱质心映射是否真的让低音在左高音在右？
  反卡手约束有效吗？谱面可复现吗（联机硬性前提）？
- `src/analysis/pipeline.test.ts` — **端到端**：合成一段已知 128/96 BPM 的鼓组，
  检查能否还原 BPM、能否区分底鼓与镲片的音色、静音输入是否优雅降级。
  因为 `analyzeMono` 只吃 `Float32Array`、不碰 Web Audio API，
  所以整条链路可以脱离浏览器验证。
- `src/chartgen/audio-derivation.test.ts` — **谱面必须真的由音频推导出来**。
  这条不变量容易被后续调参悄悄破坏：一旦谱质心映射的权重被调没，
  谱面就退化成"按节拍随机撒点"——表面看照样能玩，但与音乐再无关系。
  三个测量锁住它：音符时刻能否追溯回真实起音、音色与轨道的相关性、
  以及「抹掉音色信息后多少音符会换轨道」的消融实验。

服务端：`node server/index.js` 后另开一个终端跑 `node server/smoke-test.mjs`，
模拟两个玩家完成建房→同步→开局→结算全流程（13 项检查）。

### 真实音乐实测

用 `ffmpeg` 把 MP3 解码成 WAV，再喂给分析管线（`analyzeMono` 只吃 `Float32Array`），
可以脱离浏览器验证真实曲目：

| 曲目 | 时长 | 分析耗时 | BPM | 残差中位数 | 降级级别 |
|---|---|---|---|---|---|
| 卡农 | 3:36 | 1.6s | 114.00 | 11.6ms | L0（未降级） |
| 小星星 | 1:52 | 0.9s | 141.87 | 16.1ms | L0（未降级） |

**一个被推翻的预判**：我原本预计古典/弦乐会让节拍检测失效（并写进了文档），
**实测证明是错的**——《卡农》这类无打击乐的弦乐合奏，BPM 检测与网格对齐都正常。

但真实曲目同时暴露了一个**合成测试完全没覆盖的缺陷**：轨道分配塌缩，
详见 `docs/WORKLOG.md` 的问题 7 与 `src/chartgen/generate.test.ts` 里的回归测试。

## 已知限制

**功能性的：**

- **不提取旋律音高。** 这是跟着鼓点与音色走的下落式打点谱，**不是旋律谱**。
  浏览器端复音音高提取精度不足以支撑可玩的谱面，所以走的是
  「谱质心 → 轨道」这条路（见"架构要点 3"）。
- **对音色极度单一的素材效果有限**。若整首曲子的音色几乎没有变化，
  轨道分配会退回默认映射，谱面会偏单调。
- **节拍检测有失效的曲风**（自由节拍、无固定律动、极端变速）。
  降级链会退到"无网格模式"保证谱面仍可玩，但节奏感会弱；
  调试页可手动改 BPM 与相位。
- **手机端性能**：低端安卓上全曲分析可能耗时 8-15 秒。选「快」或「演示」档
  （后者只分析前 90 秒）。
- **Safari 对 FLAC 支持不保证**，解码失败会提示用户转成 MP3。
- **局域网 HTTP 下无离线能力**（Service Worker 需要 HTTPS）。
- **六套主题里有四套的按钮白字对比度低于 WCAG AA 的 4.5:1**：QQ 音乐 2.3:1、
  粘土拟态 2.7:1、霓虹复古 2.5:1、像素艺术 2.5–3.9:1（赛博与水墨是深字/亮字方向
  正确的组合，不受影响）。这是**照各风格规范给定的色值执行**的结果——规范既要求
  白字，又要求对比度达标，本身自相矛盾。QQ 音乐那套是知晓数值后的品牌取舍，
  其余三套若要达标，给对应主题块换一个深色的 `--btn-primary-fg` 即可。

**尚未验证的（重要）：**

- **完全没有在真实浏览器里跑过，手机端一次都没测过。** 分析算法已在
  真实音频上验证（见下），但**解码真实音频文件、Canvas 渲染效果、
  键盘与多点触摸输入、iOS 音频解锁、移动端实际性能——这些环节全是未知**。
- **真实曲目样本只有 2 首**（《卡农》《小星星》），远不足以代表各种曲风。
- **从未实机双人对战过。** 协议经过模拟验证（13 项检查全通过，RTT 1.2ms），
  但两台真实设备的同步误差与手感未测。

## 目录结构

```
src/
  types.ts              全局类型（分析与谱面单位不同：分析用秒，谱面用整数毫秒）
  analysis/             音频分析：STFT 特征 → 起音 → 测速网格
    stft.ts             单次遍历同时算出 ODF / 谱质心 / 三频段能量
    onset.ts            自适应峰值拾取 + 亚帧抛物线插值
    tempo.ts            倍频消歧 + BPM 精搜 + 四级降级链
    analysis.worker.ts  分析跑在 Worker 里，不阻塞 UI
  chartgen/             谱面生成：网格 → 量化 → 难度 → 轨道分配
    lanes.ts            ★ 轨道分配启发式（产品核心竞争力）
    audio-derivation.test.ts  ★ 锁住"谱面确实由音频推导"这条不变量
  core/                 游戏内核（零 React 依赖）
    clock.ts            ★ 主时钟与延迟补偿
    judge.ts            判定与计分
    engine.ts           ★ 游戏主类
    input.ts            键盘 + 多点触摸
    render.ts           Canvas 2D 渲染
  net/                  联机：协议 / 时钟同步 / WebSocket 客户端
  ui/                   页面
  state/                AudioContext 单例、设置持久化、主题注册表（theme.test.ts 守变量契约）
server/
  index.js              对战房间服务 + 静态托管
  smoke-test.mjs        协议冒烟测试
```
