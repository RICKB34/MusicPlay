## 二、关键决策及依据

### 决策 1：音频来源改为"用户本地文件"

**这是对原始需求的重大修改，必须记录理由。**

原需求是"识别目前正在听的音乐"。调研否掉了这条路，三条硬约束：

1. **QQ音乐无任何面向第三方的开发者接口。** 其"开放平台"是音乐人内容平台
   （上传作品、分成），不是 API 平台；客户端也没有插件/扩展 SDK。
2. **抓流物理上不可行。** `tabCapture` / `getDisplayMedia` 对 DRM 内容输出**静音**，
   拿不到可分析的 PCM；且 iOS/Android 沙盒禁止捕获其他 App 或系统音频。
3. **绕过加密明确违法。** 音频走 QMC 加密（`.mflac`/`.mgg`），解密触碰
   《著作权法》技术保护措施条款与《信息网络传播权保护条例》。

改用本地文件后，额外收获是可以做**全曲离线分析**（精度上限远高于流式）。
代码保留了 `AudioSource` 抽象接口，将来接别的来源只需加适配器。

### 决策 2：核心管线避开 `essentia.js`

调研报告推荐 `essentia.js`（WASM 音频分析全家桶），但 `npm view` 核实后发现：
**包发布于 2021-06、2022-05 后未再更新、协议是 AGPL-3.0。**

对 1-2 周的参赛项目，两个风险都不可接受：老 Emscripten 胶水能否在 Vite 8 下
打包是未知数；AGPL 有传染性，参赛作品的授权不干净。

改用一组 2026-07 发布的 MIT 库（`@audio/beat-detect` / `@audio/onset` /
`fourier-transform`）。**核实过程中还发现 `pitchfinder` 是 GPL-3.0**，
一并避开。最终依赖协议全部是 MIT / Apache-2.0。

### 决策 3：谱面质量靠"谱质心→轨道"映射，不靠音高识别

浏览器端复音音高提取做不准。与其硬啃，不如换个维度：

> 低沉的音（底鼓）→ 左侧轨；明亮的音（镲片）→ 右侧轨

这不是随机映射，而是**听觉维度到视觉维度的同构**。玩家听到底鼓时下意识知道
音符在左边，反复几次就形成"谱面在跟音乐"的感知。
而谱质心可以从已有的 STFT 里免费拿到，**零额外计算成本**。

### 决策 4：自建 Node + `ws` 而非 Colyseus / Durable Objects

只需十来种消息、两人一房间，通用框架的状态同步抽象反而要对抗。
自建的另一个决定性优势是**现场演示时可以跑在 localhost，RTT ≈ 0，网络风险归零**。

### 决策 5：TS 5.9 而非 7.0.2

TS 7 是全新的 Go 原生编译器。1-2 周的项目不该承担工具链风险，收益为零。

## 三、实测发现的问题与修复

**这一节是本次工作最有价值的部分——三个问题全都是跑起来才暴露的，静态检查一个都抓不到。**

### 问题 1：NPS 限流把谱面清空了（连带第二个缺陷）

**现象**：测试中 171 个起音的输入，只生成了 **4 个音符**。

**根因**：难度分级的 NPS 滑窗写成"窗口超限就剔除窗口内最弱者"。
当所有音符强度相同时（合成信号里很常见），比较式 `a.strength < b.strength`
**恒为假**，`weakestIdx` 永远停在 0，于是每来一个新音符就淘汰窗口里最老的那个——
谱面被从头部一路排空。

**修复**：改成**只在入口处决策，绝不回溯删除已接受的音符**。

**连带缺陷**：修完第一版后仍不对。窗口用了一个会被原地替换的数组
（`windowRefs[weakestIdx] = s`），替换后数组**不再按时间有序**，
于是"最老的"判断失效、出窗逻辑崩溃。改成每次从 `accepted` 尾部按时间回扫。

### 问题 2：96 BPM 被识别成 193 BPM（倍频错误）

**现象**：128 BPM 输入 → 检测出 130；96 BPM 输入 → 检测出 193（恰好 2 倍）。

**根因**（分两层）：
- 表层是节拍跟踪最经典的**倍频错误**：底鼓在正拍、镲片在反拍时，
  起音序列在时间上等距，"每拍一击"与"每半拍一击"在纯周期意义上无法区分。
- 深层是**我自己降级链的缺陷**：相位打分只按四分音符位置计算，
  于是当所有音符都落在反拍上时，半速网格得分恒为 0 —— 降级链不仅救不回来，
  反而会把正确答案判为最差。

**修复**：两步。① 相位打分改按**细分网格**（1/16）计算，半速网格不再被无理由惩罚；
② 候选 BPM 之间用「网格贴合度 + 节拍先验」加权比较，由先验消歧倍频。
节拍先验不是拍脑袋——人耳对 100-140 BPM 有天然偏好（Moelants 2002 共振曲线，峰值约 120）。

### 问题 3：BPM 误差 1.5%，会毁掉长曲

**现象**：128 BPM 最终得到 130，误差 1.56%。

**定位过程**：写了临时诊断脚本打印全部中间量，发现关键线索——
**起音间隔清一色是 0.2322s，而理论半拍是 0.2344s**。

**根因**：STFT 帧跳距量化。`hop=512 @22050Hz = 23.2ms` 的时间分辨率，
真实半拍 234.4ms = 10.09 帧，取整到 10 帧变成 232.2ms。
这个 0.9% 的系统误差被库和我的网格同时继承了。

诊断还显示：**128 BPM 的得分（0.840）本来就高于 130（0.622）——它本该赢，
但它根本不在候选集里**，因为候选只从库输出的 130 展开倍频，永远够不到 128。

**修复**：① **亚帧抛物线插值**——在 ODF 峰值两侧各取一帧做三点拟合，
恢复亚帧时间精度（诊断数据里可见：间隔从清一色的 0.2322 变为
0.2345/0.2322/0.2343/0.2325 在真值附近浮动）；
② **BPM 局部精搜**——用全曲几十上百个起音一起投票，搜使总量化残差最小的周期，
把帧量化的随机部分平均掉。

**效果**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| BPM | 130（误差 1.56%） | **128.07（误差 0.055%）** |
| 残差中位数 | 33.2ms | **2.94ms** |
| 降级级别 | — | L0（未降级） |

**为什么必须修**：1.56% 的速度误差累积到 3 分钟曲末是 **2.8 秒**的网格漂移，
谱面会与音乐彻底错位。

### 问题 4：轨道分配在单一音色下塌缩

**现象**：全曲音色相同的极端输入下，四轨塌缩到左半边两轨来回打。

**根因**：左右手均衡的惩罚权重太弱，压不过谱质心亲和度的梯度。

**修复**：调强权重（0.5 → 0.9）、降低触发阈值（0.25 → 0.2），
并新增**轨道冷却**机制——某条轨刚用过就在接下来若干格点内轻微扣分，
在音色信息不足时把音符铺开。

### 问题 5：服务端静态托管的两处缺陷

- **SPA 回退返回 `application/octet-stream`**：MIME 取自请求路径而非实际回退的文件。
- **缺失的 JS 资源也返回 index.html**：会把 HTML 当 JS 喂给浏览器，
  报出一堆莫名其妙的语法错误。改成只对导航请求（`Accept: text/html`）回退，
  其余返回 404。

### 问题 6：候选集锚定在库的自评上，导致正确答案进不了候选

**触发**：用户质疑"谱面是不是随机生成的？和歌曲真有关系吗？"。
为回答这个问题写了一个量化关联强度的诊断，过程中发现合成信号**反复给出
互相矛盾的错误 BPM**（157 → 104.9 → 120.0 → 189.67），于是深挖。

**根因**（两层）：

- 库在 120 BPM 的信号上返回 **200 BPM（正好顶在搜索区间上界，典型的梳状滤波退化），
  而 `confidence = 1.00`**。我拿置信度当降级开关，这么高的置信度兜底逻辑永不触发。
- 更致命的是**候选集完全锚定在库的输出上**：库给 200，其倍频只有 {200, 100, 50}，
  而正确答案 120 **永远进不了候选**——即使诊断显示 120 的贴合度得分
  （0.853）远高于所有候选（189.67 仅 0.609）也无济于事。

**修复**：候选集必须有一个**独立于库自评**的来源——无条件运行纯起音梳状搜索，
把它的结果连同倍频一并加入候选，由「贴合度 + 节拍先验」统一裁决。

**代价**：一次额外的梳状搜索。把步长放宽到 1 BPM（精度由后续局部精搜保证）
后，对几千个起音的曲目约 0.1-0.2 秒，跑在 Worker 里可忽略。

**为什么这一定是真实缺陷而非合成信号假象**：只要库在某个曲子上给出
高置信度的错误答案，旧架构就永远救不回来。真实音乐完全可能出现这种情况。

**顺带的反直觉发现**：一度担心"真实音乐比合成信号更难检测"，对照实验证明相反——

| 信号 | 检出 BPM | 误差 |
|---|---|---|
| 机器级完美规整 | 104.90 | −12.58% |
| 加时间抖动 + 力度起伏 | **120.00** | **0.00%** |

机器级完美的周期信号里，每 0.25s / 0.5s / 1.0s 全部严格周期，
梳状滤波找不到唯一的"拍"。**真实演奏天然的时间抖动反而消除了这个歧义。**

**同期改进**：相位与网格打分改为**按起音强度加权**。节拍是由重音定义的，
不是由最密集的起音流定义的——等权处理时，反拍上密集的弱镲片会淹没
正拍上底鼓携带的节拍信息。

**新增测试**：`src/chartgen/audio-derivation.test.ts` 把"谱面确实由音频推导"
固化为不变量。这类退化（谱面变成"按节拍随机撒点"）**表面看不出来**——
谱子照样能玩，但与音乐再无关系，必须靠测试守住。

### 问题 7：轨道分配在真实音乐上塌缩（合成测试完全没覆盖）

**触发**：用户往项目里放了 `test_music/卡农.mp3`，开发服务器随即崩溃：

```
EBUSY: watch … D:\code\HACKATHON\test_music\卡农.mp3
```

Vite 的 fs watcher 监视整个项目目录，碰到被占用的二进制大文件会抛错并**整个进程退出**。
音频文件本来也不需要热重载，已在 `vite.config.ts` 的 `server.watch.ignored` 中排除。

**但这个崩溃带来了一次意外收获**：借机用 `ffmpeg` 解码 MP3 → WAV，
再喂给 `analyzeMono`（它只吃 `Float32Array`，不碰 Web Audio API），
**首次在真实音乐上跑通了整条分析管线**。

#### 7.1 一个被推翻的预判

我原本预计古典/弦乐会让节拍检测失效，并把这条写进了 README 与工作日志。
**实测证明是错的**：

| 曲目 | 时长 | 分析耗时 | BPM | 残差中位数 | 降级级别 |
|---|---|---|---|---|---|
| 卡农（弦乐合奏，无打击乐） | 3:36 | 1.6s | 114.00 | 11.6ms | L0 |
| 小星星 | 1:52 | 0.9s | 141.87 | 16.1ms | L0 |

两首都 **L0 未降级、残差 11-16ms、质量判定 good**。3 分 36 秒的曲子分析只用 1.6 秒。
已在 README 更正这条预判。

#### 7.2 真实缺陷：轨道分配塌缩

但真实曲目暴露了合成测试**完全没覆盖**的问题：

```
卡农   轨道使用率 65% / 2% / 33% / 0%   ← 第 4 轨完全没用上
小星星 轨道使用率 10% / 51% / 26% / 13%
```

**根因**：`centroidToLane` 用的是**固定绝对区间**（200Hz→最左，6000Hz→最右），
而真实弦乐的谱质心全曲只在 **602–1094Hz** 之间——全都挤在映射区间的最左端，
自然全落到第 0 轨。

合成测试之所以没抓到，是因为我的合成信号音色跨度都很大
（底鼓 80Hz 到镲片 6000Hz），**恰好避开了窄音色范围这种真实情况**。

**修复**：映射区间改为由**本曲自己的音色分布**推算（取 p10/p90 归一化）。
映射关系（相对明暗 → 左右）不变，但能真正铺满所有轨道。
这与设计初衷一致——玩家感知的是**相对**明暗，不是绝对频率。

#### 7.3 连带发现的第二个设计错误

第一版修复后，`hard` 难度正常了，但 `easy`/`normal` 仍然塌缩。
原因是我把映射区间算在了**难度筛选之后**的音符上：简单难度只保留最突出的音，
它们的音色分布更窄，触发了"范围过窄就退回固定区间"的兜底。

**这是设计错误**：映射区间应当是**歌曲的属性**，与难度无关。
改为从**全曲所有起音**推算后，三个难度全部正常。

#### 7.4 第三个错误：阈值定错了量纲

我最初把"音色范围过窄"的阈值定在 400Hz，结果把《卡农》这类弦乐
（跨度约 350-490Hz）误判成"没有音色变化"。

**绝对值本身就是错误的判据**——350Hz 的跨度在 850Hz 附近是 **40% 的相对变化**，
那是真实的音色差异，铺开到四条轨上恰恰是正确的做法。
这个分支的唯一职责应该是**防止除以零**，而不是判断"变化够不够大"。
已下调到 120Hz 并注释说明。

#### 7.5 修复效果

| 曲目 / 难度 | 修复前 | 修复后 |
|---|---|---|
| 卡农 easy | 65% / 2% / 33% / **0%** | **2% / 39% / 29% / 29%** |
| 卡农 normal | 64% / 2% / 32% / 2% | **7% / 36% / 32% / 25%** |
| 卡农 hard | 19% / 30% / 31% / 20% | 11% / 34% / 32% / 23% |
| 小星星 easy | 10% / **51%** / 26% / 13% | **31% / 31% / 24% / 14%** |
| 小星星 normal | 10% / **51%** / 26% / 13% | **30% / 31% / 31% / 8%** |

**新增回归测试**（`src/chartgen/generate.test.ts`）：
模拟弦乐合奏那种窄音色范围，断言四轨使用率都不低于 8%；
并断言同一首歌换难度时映射区间不变。只要有人把自适应区间改回固定区间，测试立刻会红。

**这次的教训**：合成测试信号即使经过精心设计，也会因为
「作者下意识地让参数分离得很好」而避开真实数据的困难之处。
**必须尽早用真实素材验证。**

但与音乐再无关系。没有测试就只能靠肉眼怀疑。

### 对战服务冒烟测试（13 项全通过，`node server/smoke-test.mjs`）

**产出**：两条新链路 —— ①**按段落**混合人声轨与原曲来生成谱面；②长按（hold）音符的完整实现

### 关键决策及依据

**决策 1：分段混合在 onset 层做，不拼音频**

用户要的是"伴奏段用原曲、人声段用人声轨，滤去伴奏"。实现上有两条路：

- **时域拼接**一条"混合音频"（这段取人声、那段取原曲），喂给现有分析管线。无需改任何分析代码，
  但会**毁掉 BPM 检测**——人声轨在间奏是静音的，梳状滤波拿不到持续能量。
- **onset 层混合**（采用）：两条轨各跑一遍 STFT + 起音检测，再按人声活跃区间筛选合并。

选后者的理由：`TrackAnalysis.onsets` 是音轨来源留下的**唯一痕迹**。一旦 onsets 定下来，后面的
测速、网格、量化、难度、轨道分配全都不关心它从哪来——所以 `chartgen/` 一行都不用改。
代价是两次 STFT + 两次起音检测（4 分钟的歌约 4-8 秒）。

**决策 2：节拍网格永远从原曲推**

`finalizeAnalysis` 的 `data` 参数会喂给 `estimateTempo` → `@audio/beat-detect` 的梳状滤波，
它需要贯穿全曲的持续能量。人声轨在间奏静音，用它测速会让 BPM 置信度崩掉并触发降级链，
反而毁掉谱面质量。

结论：**网格跟整首歌的律动走，音符来源按段混合。**

**决策 3：人声活跃判定的参数靠实测校准**

初版参数（平滑 10 帧 / 桥接 0.3s）在真实曲目上切出 **66 个碎片段**（均长 1.3 秒），
谱面会在原曲与人声之间每 1.3 秒横跳一次。根因是 Demucs 残留——该曲人声轨的背景 RMS
高达 0.085（p50），阈值被反复穿越。

调到平滑 30 帧 / 桥接 1.0s 后：**10 段、均长 8.4 秒**。

划分有效性自检：区间内 RMS 均值 0.130 vs 区间外 0.053，**2.43 倍**。另外试过把阈值调严
（在 p50 与 p85 之间取向 0.6），结果**把 0-72 秒的主歌全漏掉了**，所以阈值保持 0.4。

**决策 4：hold 必须动 `chartgen` —— "不改生成逻辑"与"要吸收"不可兼得**

参考版本的 `decideHolds` 跑在 `applyDifficulty` **之后**、`assignLanes` **之前**，因为它的核心是
**吸收**：把长按区间内音色相近、自身也延续很长的音符**从谱面里删掉**。

参考版本的原文注释说得很清楚——"只打标记不删音符"的初版是**加压而非简化**：实测九个
（曲目 × 难度）组合里八个的音符总数**一模一样**。吸收必须发生在分轨前，那就在 `chartgen`
内部。所以"chartgen 一行不动"这个约束**技术上不可能满足**。

需要更正的是：**我最初给的方案描述低估了改动范围**（说"只加 `generate.ts` 一行"，
实际动了 4 个现有文件：`quantize` / `difficulty` / `lanes` / `generate`）。用户在我纠正后批准继续。

补偿手段：`GenerateOptions.holds: false` 时**完全跳过**长按判定，谱面与改动前逐字节一致。
原有 28 个测试**一行没改就全过**（合成起音的 `sustainMs` 填 0，永远不会触发生成长按）。

**决策 5：尾判容差 120 → 180ms，断触 miss → good 封顶**

联网调研主流音游的 hold 判定：

| | tap 窗口 | hold 尾判容差 | 比例 |
|---|---|---|---|
| 本项目（改前） | good 90ms | 120ms | 1.33×（最紧） |
| osu!mania ScoreV2/lazer | — | 1.5× 正常窗 | 1.5× |
| Etterna J4 | 90ms | hold_window 250ms | 2.8× |

180ms = `goodMs` 的 **2 倍**，落在主流区间。同时把 `HOLD_TAIL_MIN_GAP_MS` 从 220 → **280**
—— 这两个常量**耦合**（原值 220 = 120 + 90 + 余量），只放宽松手容差而不动它，会出现
"玩家还在容差内可以松手，但同轨下一个音符已经落下来了"，等于把宽容度从轨道分配那侧又收回去。

断触从 `miss` 改为封顶 `good`：玩家确实按住了头和一段，判 miss 否定掉已完成的部分，太严苛。
主流做法（osu!mania 的 *hold break*）就是把这一下**封顶**而不是作废。
与 osu! 的差别：那边断触会重置 combo，我们这里仍是一次正常 good、combo 继续——要断 combo
得动计分器内部状态，代价大于收益。

### 踩过的坑

**坑 1：缓存 key 的维度加了两次（严重）**

客户端缓存 key 改成 `${指纹}|${版本}|${轨}`，同时服务端 `cachePathFor(key, track)` 又按 track
加一次后缀。结果是磁盘上已有的 `xxx_htdemucs-v1.wav` **永远命不中**，每次请求都当缓存 miss
→ **重跑 3 分钟分离**。

更广：所有预热缓存全部失效。

修复：服务端 key 不含 track（磁盘名由它与 track 参数共同决定，且保持与旧版一致），
本地 IndexedDB key 含 track（四轨存同一仓库，不分开会互相覆盖）。

分叉——包括"断触后不会被 `settleHolds` 结算第二次"这类会导致一个音符算两分的错误。

### 关键决策及依据

**决策 1：主题变量存"完整属性值"，不拆零件**

两套主题的差异**不只是颜色**，还包括圆角 / 硬边偏移阴影 / 扫描线 / 文字倾斜 /
全大写等宽字体 / 动效曲线。最初想按常规做法拆成 `--shadow-x` / `--shadow-blur` /
`--shadow-color` 这类零件，但拆不动：

- 赛博是 `4px 4px 0 #a020f0`（零模糊、单层），QQ 是 `0 1px 3px rgba(0,0,0,.06), 0 1px 2px …`
  （柔和、多层）——**结构不同**，不是同一组零件换值。
- `box-shadow` 是逗号列表，`none` 只能作为**整体值**，`box-shadow: var(--a), var(--b)`
  在 `--a: none` 时整条声明非法。

所以变量存整个 `box-shadow` / 整个 `border` 简写。代价是每处组件规则都得走变量，
好处是形状差异能在一个变量里表达干净。

**决策 2：变体类只赋变量，状态规则只声明属性**

按钮有 3 个变体（默认 / `.primary` / `.ghost`）× 4 个状态（常态 / hover / active / disabled），
按常规写法是 12 条以上互相打架的规则，且每个变体都要重写一遍 hover。

改用变量间接后：**状态规则只写 4 条**，变体类只赋 `--btn-*` 变量。依据是自定义属性
**是继承的、在元素上解析、与状态无关**——所以 `.seg button { --lift: none }` 这种低特异性
赋值也能生效，`button:hover` 里读到的就是变体覆盖后的值。于是 `.seg button:hover`、
`.primary:hover` 这类"变体 × 状态"的覆盖规则可以**整条删掉**。

**决策 3：canvas 与 CSS 用两份调色板，接受重复**

游戏画面是 canvas 绘制的，拿不到 CSS 变量。三条路：

- **JS 生成 CSS 变量注入 `<style>`** —— 真单一来源，但样式表要到 JS 执行后才存在，
  与"首屏防闪烁"直接冲突。否决。
- **`getComputedStyle` 读 CSS 变量** —— 可以，但有时序陷阱（必须先写 `data-theme` 再读，
  同一 tick 内可能拿到旧值）、且读不到时返回**空字符串**，`ctx.fillStyle = ''` 会被
  **静默忽略**、沿用上一帧颜色（残影）。更关键的是**绝不能放进 `render()`**——
  每帧 `getComputedStyle` 会强制样式重算。
- **两份独立定义**（采用）—— 实际重复量很小：`RenderTheme` 的 17 个字段里 CSS 侧只需要 6 个，
  反过来 CSS 的 `--card-shadow` / `--btn-*` / `--seg-*` canvas 也完全不需要。

代价是改色要改两处，所以在 `styles.css` 主题块和 `render.ts` 的两个主题对象上
**互加了交叉引用注释**。

**决策 4：`#31C27C` 只能当填充色，不能当文字色**

品牌绿相对亮度 `L=0.4069`，实测对比度：

| 前景 on 背景 | 对比度 | 判定 |
|---|---|---|
| 白字 on `#31C27C` | **2.30:1** | ✗ 低于 AA 的 4.5:1，连大字的 3:1 都不到 |
| 深墨绿 on `#31C27C` | 7.57:1 | ✓ AA + AAA |
| `#31C27C` 当文字 on 白底 | **2.30:1** | ✗ 同样不达标 |
| `#0A7F4D` 当文字 on 白底 | 5.05:1 | ✓ AA |

结论：品牌绿只用于**音符、判定线、选中态填充**这类大色块；正文、图标、焦点环、
以及白底上的绿色文字一律用深绿 `#0A7F4D`。这一条是第二轮里最影响观感的判断——
如果不做这个区分，QQ 主题下所有绿色文字都会糊在白底上。

**决策 5：主按钮仍用绿底白字（用户拍板，已知不达标）**

按决策 4 的推导，主按钮应改用深色文字才能达标。但 QQ 音乐 App 的主按钮就是绿底白字，
用户在被明确告知 2.30:1 这个数字后**选择了贴合品牌**。

处理方式：只在按钮**填充**上放行，其余场景全部用深绿；并在 `styles.css` 的主题块里
写明「这是有意的品牌取舍，不要顺手修」，避免以后被当成 bug 改掉。

**决策 6：调试页的配色有意不跟主题**

`DebugChart.tsx` 的画布有约 25 处硬编码的酸性色。它是开发者诊断工具、不在演示路径上，
而波形 / 网格 / 残差需要的是一组**高对比度的固定色阶**——跟着主题换成白底反而看不清细线。
所以保留酸性配色，并在文件头写明这是有意的，**要改就整体替换，别只改一半**。

### 踩过的坑

**坑 1：语义别名形同虚设（严重，是我上一轮自己埋的）**

第一轮我重写 `styles.css` 时，在 `:root` 里定义了 `--accent` / `--border` / `--danger`
这一层语义别名，注释还写着「各组件不必改动即可换肤」。但实际写组件规则时，
**我全程直接引用了 `--acid-green` / `--purple` / `--acid-yellow` / `--cyber-pink`**。

实测统计：`styles.css` 里调色板直引 **55 处**（`--acid-green` 27、`--purple` 14、
`--acid-yellow` 11、`--cyber-pink` 7），而 `--accent` / `--border` / `--success` /
`--danger` / `--warning` 在该文件里的出现次数是 **0**（只有 TSX 内联样式在用）。

后果：如果直接加 `data-theme` 只覆盖别名，QQ 主题下卡片的紫色阴影、`.stat` 边框、
`.note` 边框、`.brand` / `.grade` 的镀影**全会漏出酸性配色**。

**教训**：注释里写的架构意图不等于代码真的按那个意图写了。这层别名是给"未来换肤"
预留的，但预留了却没走，等于没预留。**要验证这类事情只能靠 grep 数引用次数，
不能靠读注释。**

**坑 2：`.progress` 加边框吃掉内联高度（我引入的回归）**

第一轮我按酸性风给 `.progress` 加了 `border: 2px solid`。但游戏页那条**对手进度条**
传了内联 `height: 4`，在 `border-box` 下上下边框正好吃掉全部内容高度 → 填充条永远
显示成满进度。

修复：改用 `box-shadow: 0 0 0 2px` 做外描边（不占布局空间），并在 CSS 注释里写明了原因。
这是**只有实际跑起来看画面才会发现**的问题——类型检查、构建、单元测试全都不会报。

**坑 3：内联样式无法被 CSS 覆盖，导致倒计时数字消失**

`GameScreen.tsx` 的倒计时遮罩是**内联样式** `background: rgba(10,10,10,0.72)`。
内联样式的优先级高于任何 CSS 类，所以主题切换压根管不到它。

而倒计时数字的颜色继承自 `body` 的 `--text`——QQ 主题下 `--text` 是深灰 `#1A1A1A`，
叠在 0.72 的深色遮罩上 = **深字压深底，直接看不见**。

修复：删掉内联的固定色，改为内联引用 `var(--overlay-scrim-soft)`，遮罩随主题走。
（拆成 soft 版是因为原来的 0.72 比 `.overlay` 默认的 0.92 更透，让玩家在倒计时时
还能看到背景，这个意图保留。）

**坑 4：三处"字看不见"的硬编码**

主题化时逐项核对对比度，揪出三处会在 QQ 主题下失效的写死值：

| 位置 | 问题 | QQ 主题下的对比度 |
|---|---|---|
| `--danger` / `--warning` | 指向赛博粉 / 酸性黄 | 1.9:1 / 1.2:1，**5 个页面拿它们当正文级错误文字** |
| `--success` | 指向荧光绿 | 1.3:1 |
| 判定色 `#e6ff00` | 白底画布上的"great"判定 | 亮度 0.88，**在白底上等于消失** |

这三处都不是"颜色不好看"，而是**功能性的不可读**。逐项换成深色版本后才可用。

**坑 5：验证脚本自己被 headless 环境卡住**

首轮截图时页面停在起始页不动，一度以为点击逻辑写错了。实际原因是
**headless 没有音频输出设备，`AudioContext.resume()` 永不 resolve**，而
`StartScreen` 的 `onStart` 是 `await unlockAudio()` ——整个流程卡在 await 上。

解法是注入桩让 `ctx.state` 直接返回 `'running'`。这是**验证手段自身的问题**，
不是产品缺陷，但一度误导了排查方向。

**产出**：① 主题选择器从分段控件改成「按钮 → 展开面板」；② 新增四套主题
（`粘土拟态` / `霓虹复古` / `像素艺术` / `水墨画风`），主题总数 2 → **6**；
③ 加主题的改动面从 7 个文件收敛到 **3 个**。测试 49 → **56 个**。

**状态**：六套主题全部经 headless 浏览器截图逐套人眼确认；`tsc` / 测试 / 构建全绿。
**四套主题的按钮白字对比度低于 AA，未修**（见文末遗留 2）。

### 背景

用户按 `STYLEKIT_STYLE_REFERENCE` 格式的规范文档依次投喂风格规范，每份都是
「Hard Prompt + Token 字典 + 禁止项 + 自检清单」的结构，内容全是 Tailwind class，
而本项目用的是 CSS 自定义属性主题系统——**每一份都要做一次转译**。

本次还有一个明确的产品反馈：分段控件形式的主题选择器「可选项太少」，
要求改成能展开多个选项的按钮。这是本轮重构的直接起因。

### 关键决策及依据

**决策 1：展开面板走进文档流，不做绝对定位浮层**

`.screen` 是 `overflow-y: auto` 的滚动容器。浮层挂在卡片上，当卡片靠近页面底部时
**菜单会被容器裁掉**——不是画在视口外，是直接消失。移动端还容易顶出视口。

改成文档流内展开（把下方内容推开），代价是页面变长，换来零裁切、零定位计算。
对一个低频的选主题操作，这个交换划算。

**决策 2：选中态不复用 `--seg-active-*`**

分段控件的选中态是「饱和底 + 白字」，那是为**单个短标签**设计的。主题选项里却是
「主题名 + 一整句说明」两行文字，白字压在 `#31c27c` 上只有 2.3:1，说明文字再叠一档
透明度直接掉到 **1.9:1**（截图里确实是糊的）。

改用「淡色底 + 深色字 + 描边」，同 `.badge.good` 的手法，三套有值的主题都在 4.5:1 以上。
为此新增了 `--pick-active-bg` / `--pick-active-fg` / `--pick-active-border-c` 三个变量。

**决策 3：加主题只动三处——靠注册表 + 遍历式测试锁住**

原来加一套主题要改 7 个文件（含 UI 里硬编码的三元表达式和写死 `acid` 的测试）。
本轮做了两件事把它压到 3 处：

- `ThemeDef` 承载 UI 需要的一切（名字 / 说明 / 色卡 / 状态栏色），选择器只遍历 `THEMES`，
  `App.tsx` 里那个 `theme === 'acid' ? '#0a0a0a' : '#31c27c'` 的三元也随之删掉。
- `normalizeThemeKey` 从 `value === 'acid' ? ... : ...` 改成 `THEMES.some(...)`
  ——**写死字面量的收敛函数是新主题最容易漏的一处**（新主题进了列表却永远切不过去，
  且不报错）。

效果：本轮第 4、5、6 套主题各自只改了 `theme.ts` + `render.ts` + `styles.css`，
`ThemePicker.tsx` 和 `theme.test.ts` 一行未动。

**决策 4：规范化内部冲突时，禁止项优先**

规范文档里频繁出现**同一文档自相矛盾**，且都是「REQUIRED 要 A」+「禁止项禁 A」：

| 主题 | 冲突 | 取舍 |
|---|---|---|
| 霓虹复古 | REQUIRE `bg-clip-text` 渐变标题 ↔ 自检清单明确禁止 `background-clip: text` | 取禁止，改用双色 `text-shadow` 重影 |
| 像素艺术 | 禁止一切 `transition-*` ↔ Token 字典写 `duration-100` | 取禁止，`--dur: 0ms` |
| 粘土拟态 | 禁止 `translate-y` 代替形变 ↔ 交互表又要 `hover:translate-y-1` | 位移给 hover（浮起），形变给 active（压扁），两者分工不冲突 |

依据是硬提示里那句「遇到冲突时以禁止项为最高优先级」。每次取舍都写进了对应主题块
的注释，避免后来者当成 bug 改回去。

**决策 5：`--dur: 0ms` 表达像素风的「Absolute Zero」**

像素风要求全站 `transition-none`（"像素游戏是状态机，不是动画引擎"）。
本项目所有动效时长都取自 `--dur`（按钮、进度条、箭头旋转、面板入场），
所以置 0 就等价于全站硬切，**不必逐个组件去写 `transition: none`**。
`--ease` 此时无意义，给 `linear` 只为满足「变量必须有值」的契约。

**决策 6：规范要"半透明表面"时改成不透明**

霓虹规范给的卡片是 `bg-[#1a0a2e]/60`。直接照做会出事：主题选项、统计块、输入框
都嵌在卡片里，**半透明叠半透明 = 每层都比上一层亮**，视觉上正是自检清单禁止的
「卡片里套卡片」。

改法是取「卡片叠完之后的实际色值」直接写死，层级改用明度差表达：内嵌块比卡片亮
一档（`#320a52`），凹陷块比卡片暗一档（`#1e0b38`）。

**决策 7：抽出 `--btn-border-w` 与 `--dot-radius`**

两处硬编码挡住了新规范，且都是**只在特定主题下才暴露**的问题：

- `button { border: 2px solid var(--btn-border-c) }`——宽度写死。像素风要 `border-4`，
  水墨要「只有一条底边线」（`border-b`）。宽度抽成变量后，水墨用 `--btn-border-w: 1px`
  + 透明色 + `inset 0 -1px 0` 的阴影模拟底边线，**没有动全局 button 的四边 border 结构**。
- `.theme-dots i { border-radius: 999px }`——色卡圆点写死圆形。像素风禁止**任何**圆角，
  色卡也得是方块。抽成 `--dot-radius`。

像素风的「Pixel Perfect Drop」要求位移量与阴影偏移量**必须精确相等**（不等就穿帮），
所以 `--lift` / `--press` / `--btn-shadow` 的 4px 是一组，注释里标了「改要一起改」。

### 踩过的坑

**坑 1：多列面板的账，我算了三遍才算对**

| 方案 | 结果 |
|---|---|
| `minmax(190px)` → 3 列 | 每列 200px，主题名 + 说明挤成两三行 |
| `minmax(240px)` → 2 列 | 第三个主题落单占半行，右边空一块 |
| `1fr` → 单列 | 3 个主题时最整齐，**到 6 个主题要吃掉半个屏幕** |
| `minmax(280px)` → 2 列（最终） | 6 个主题 3 行，面板高度砍半；奇数个时末项落单 |

教训：**列数是随数据量变化的，不能一次定死。** 定 3 个主题时的最优解，到 6 个时
就变成了最差解。上一版注释里我还写了「主题数量只会往上加，任何固定列数都会在某个
数量上留空洞」——道理写对了，结论却选反了（当时选了单列，恰恰是数量多时最差的那个）。

**坑 2：验证手段自身的两个 headless 陷阱**

- `--headless=new` 在本机**不输出截图文件**（无报错，静默失败），必须用旧版 `--headless`。
- 连续截图时 Edge 会**复用已有实例**，后续调用直接返回、不落文件。要加 `--user-data-dir`
  逐次隔离。
- 面板的入场动画会让 `--virtual-time-budget` **卡在起始帧**：截图里所有选项都是透明的，
  一度以为配色写错了。预览页里设 `animation: none` 后才看到真容。

**坑 3：两次编辑之间的瞬时中间态**

改 `SongSelect.tsx` 时分了两步：先删 `THEMES` 的 import，再替换 JSX。这中间 HMR
热更新了一次，报 `An error occurred in the <SongSelect> component`。是我的编辑顺序问题，
不是产品缺陷——但它出现在 vite 日志里，**看到日志里的报错要先对时间戳**，
别急着当成真实缺陷去排查。

**坑 4：规范里的"正文色"经常不能当正文用**

多份规范给的正文辅助色对比度都不够，且差距不小：

| 主题 | 规范原值 | 对比度 | 实际采用 |
|---|---|---|---|
| 水墨 | `text-[#a89279]` 茶褐 | 2.7:1 | `#7d6b56`（同色相压暗）4.7:1 |
| 水墨 | `text-[#c4b9a8]` 沙色 | 1.9:1 | 未采用 |
| 霓虹 | `text-[#b967ff]/70` | 3.4:1 | 全不透明 `#b967ff` 5.7:1 |

处理原则：保留色相，压暗明度，让正文过 AA。糖果色/霓虹色留给填充块（音符、按钮、
进度条），文字一律深化。

**坑 5：`--fw-heading: 300` 在中文下看不到效果**

## 2026-09-29 · 鼓点反馈、手机端独立 App、以及两次被真机推翻的决策

**产出**：鼓点驱动的边框光晕；一个可离线游玩的 Android APK（4.06 MB）。
过程中试过两条路（浏览器内人声分离、横屏）都做完了又撤掉，理由记在下面。

**这一节的重点不是"做了什么"，而是"为什么撤了什么"** —— 三条改动都是被
真机反馈推翻的，桌面上的判断全都不作数。

---

### 一、鼓点反馈：从四种做到一种

起因是"加震动反馈，只在人声分离过后生效，按分离出的鼓做"。

**实现顺序与每次的结论**：

| 反馈 | 做法 | 结局 |
|---|---|---|
| 手机马达 | `navigator.vibrate(10–22ms)`，120ms 节流 | **删除** |
| 画面整体平移 | 游戏世界 `ctx.translate` | **删除**（读谱时参照物全在晃） |
| 判定线抖动 | 只位移判定线 y，4px，90ms 衰减 | **删除** |
| 边框光晕 | DOM 层 `inset box-shadow`，逐帧写 opacity | **保留** |

真机反馈是"震动太明显导致很卡顿"。卡顿的来源是抖动：它每帧位移判定线，
逼着画布重绘一块本来静止的区域；而光晕只是合成层的 opacity 变化，不触发
重绘。**"轻微"这个要求在桌面浏览器上根本测不出来** —— 没有马达，也感受不到
持续位移对读谱的干扰。

**光晕的两处关键实现**：

1. 颜色取 `--accent` 而不是逐主题写死 —— 六套主题各自都定义了这个变量，
   加主题时这里不用动，天然"和当前主题色匹配"。
2. 只靠 opacity 做脉冲。第一版用 60% 浓度 + 80px 半径，截图发现白底主题的
   整块可玩区域都被染绿、音符对比度被吃掉。收到 40%/52px 后真机反馈"不够
   明显"，最终定在 **58% / 20px + 84px** —— 边缘明显、中间干净。

**鼓点的两个来源**（因为没有分离结果时也得有反馈）：

1. 分离出的鼓轨 —— 用 `detectOnsets`，参数 delta=1.6 / minGapMs=70，
   再按归一化强度砍掉 30% 以下（滤掉 hi-hat）。
2. **原曲的起音列表**（`analysis.onsets`，谱面分析已算好的副产品）——
   按音色筛选：`lowRatio >= 0.30 || highRatio >= 0.25`。

第 2 条在真实曲目上验证过，数据如下（默认门限）：

| 曲目 | 检出密度 | 每拍 | lowRatio 中位 | 判断 |
|---|---|---|---|---|
| BE ME（流行，有鼓） | 1.77 个/秒 | 1.20 | 0.44 | 接近理想 |
| 小星星 | 0.77 个/秒 | 0.32 | 0.07 | 打击乐稀疏 |
| 卡农（弦乐，无打击乐） | 7 个 | 0.02 | 0.07 | **几乎不误报** ✓ |

卡农是关键证据：它本来就是无打击乐的弦乐合奏，筛选结果几乎为空，
说明人声与旋律**不会**被大量误判成鼓点。`lowRatio` 中位数把"有鼓"（0.44）
和"无鼓"（0.07）分得很开，0.30 的门限正好落在中间。

### 二、手机端：从"连电脑"到独立 APK

用户最初的诉求是"手机端独立运行"，我理解偏了 —— 先做成"手机连同一 WiFi
访问电脑的页面"，被纠正后才回到正轨：**要的是装到手机上的 APK**。

**演进路径**：

1. 最简单验证版 APK（只有一个分离页面）—— 用户装上跑通，反馈"效果可以接受"
2. 完整音游 + 内置模型 —— 用户装上跑通，反馈三个问题（见下）

**APK 的关键约束**：模型必须内置，运行时不能依赖任何网络。

---

### 三、被放弃的两条路（含理由与数据）

#### 1. htdemucs 无法在浏览器里运行

原本想把现有的 htdemucs（也是服务端在用的那个）搬到浏览器内跑，让手机
离线也能分离。**结论：能跑通 session 创建才算数，而它连这步都过不去。**

实测（桌面 Edge，16 核，WebGPU 可用，跨源隔离三件套齐全）：

```
Can't create a session. ERROR_CODE: 6, ERROR_MESSAGE: std::bad_alloc
```

排除过程：

| 猜测 | 结果 |
|---|---|
| 线程数太多 | 1/4/8 全部失败 |
| 图优化吃内存 | all / extended / basic / disabled 全部失败 |
| 走了 WASM 而非 WebGPU | WebGPU adapter 可获取，切 EP 后**同样报错** |
| 权重内嵌撑爆内存 | 转 external data（158MB → 77.7+80.3MB）后**仍然失败** |

根因：**ONNX Runtime Web 编译时没开 Emscripten 的 `MAXIMUM_MEMORY`**，
默认只有 2GB 的 32 位 WASM 堆（实测约 1.5GB 可用）。而 htdemucs 有
**24917 个节点**，77.7MB 的图结构本身在 WASM 里解析建图就顶穿了 —— 这也是
为什么 external data 和 INT8 量化都救不了：它们是减**权重**的，而瓶颈是
**图结构**。

**对照实验**（这是确认结论的关键）：用 `onnx` 现场生成一个 103 字节的
tiny.onnx（一个 Add 节点），同一个页面里加载 —— **成功，推理输出正确**。
所以 ORT Web、跨源隔离、WebGPU、多线程、external data 传输全都是好的，
问题纯粹是模型规模。

（顺带一个 export 细节：用 onnx 1.23 生成的模型默认 IR v14，而 ORT Web
只支持到 v13，会报 `Unsupported model IR version: 14`。需要显式
`model.ir_version = 13`。）

#### 2. Spleeter 能跑，但质量不如不加

换用 Spleeter 2stems（**218 个节点**，18.8MB ×2）后一次就通了：

- 模型加载 1.9 秒
- 60 秒音频 20 秒处理（桌面单线程，RTF 0.33）
- 输出能量占原曲 **17.5%** —— 人声的合理量级，说明分离是对的

算法照搬 sherpa-onnx 的 `offline-source-separation-spleeter-impl.h`：
ONNX 里只有 U-Net，STFT（4096/1024/hann）、iSTFT、以及**两个模型输出做
Wiener 归一化**都得自己实现（少这一步 mask 不在 [0,1] 内，重建会失真）。

**但用户真机实测后要求删掉**："分离效果太差，甚至不如不加"。

这与事前查到的资料一致：Spleeter 的 SDR 是 5.12 dB，htdemucs 是 8.11 dB；
50 位音频工程师盲听里 Demucs 82% : Spleeter 12%。当时判断"vocals 是
Spleeter 最不弱的轨（6.86 vs 7.05）"可能够用，**实测否决了这个判断**。

**移除得很彻底**：代码（`spleeterLocal.ts`）、降级链、38MB 模型、
`onnxruntime-web` 依赖、构建开关（`.env.app` / `build:app`）、以及 UI 上
那个人声分离选项（探测不到服务时整张卡片隐藏）。网页端 dist 从 66MB 回到
390KB。

#### 3. 横屏：做了又撤回

用户反馈"不支持横屏游玩"，根因是 `AndroidManifest.xml` 里**根本没有
`screenOrientation`** 属性。设成 `sensorLandscape` 后用户要求"调回竖屏"，
于是改成 `portrait` 锁定，并把为横屏加的那段 CSS（按视口高度反推画布宽度
上限）一并撤掉 —— 它只在横屏下生效，留着是死代码。

---

### 四、判定规则放松

**需求**："改松判定规则，只要 combo 上了就算 perfect，不降低准确度"。

改动只在 `Scorer.apply` 一处：非 miss 的判定一律按 `JUDGMENT_VALUE.perfect`
计分、权重记 1。

**刻意没改的**：

- 判定窗口（`perfectMs` / `greatMs` / `goodMs`）原值不动 —— 按得准不准
  仍被如实测量，只是不再据此惩罚
- `counts` 仍记**真实判定** —— 结算页能看出自己有多少个 great
- 打击特效颜色仍跟真实判定

所以会出现"Perfect 10 / Great 20 但准确度 100% 评级 S"的画面。这是"保留
反馈、去掉惩罚"的直接结果，已在日志里说明可选的其他调法。

新增 4 个测试钉住新规则（此前 `Scorer` 完全没有测试覆盖 —— 改了计分规则
却没有任何测试失败，这本身就是个信号）。

### 五、踩到的坑（都不是业务逻辑，但都很费时间）

1. **Gradle 下载中断**：`services.gradle.org` 下到 91MB 时 SSL 断开。
   换腾讯镜像 `mirrors.cloud.tencent.com/gradle/` 后正常，并把
   `networkTimeout` 从 10s 提到 120s。

2. **增量构建产生 51MB 的假 APK**：删掉 38MB 模型后 APK 仍是 51MB。
   用 Python 核账发现真实内容压缩后只有 **3.98MB**，差额 47MB 全是上一次
   构建留下的垃圾（Gradle 追加内容却没截断文件）。`clean` 后 4.06MB。
   打包脚本已加上 `clean`。

3. **重采样公式多除了一个采样率**：`frames = duration * SR / srcRate`，
   正确是 `duration * SR`。后果是 112 秒的音频被渲染成 103 帧（0.002 秒），
   整条链拿到空音频。现象是"分离秒完成、输出长度为 0"。

4. **headless 浏览器验证不了异步**：
   - `--virtual-time-budget` 会冻结网络，模块 Worker 拉不到依赖
   - `--dump-dom` 不等 load 事件
   - `AudioContext.resume()` 在 headless 下永不 resolve，页面卡在起始页
     （注入 mock 也没绕过去）
   
   结论：**验证异步行为必须用 CDP 轮询**，静态观感才用截图。

5. **WASM 路径的两种写法**：`wasmPaths` 接受 `string`（目录）或
   `{ wasm?: URL|string, mjs?: URL|string }`，**不是文件名到 URL 的映射**。
   Vite 会给 wasm 加内容 hash，所以必须用 `?url` 导入后传 `.wasm` 字段。

## 2026-09-29 · 长按判定收紧与双押（阈值下调 + 主动注入）

**需求**：① 长按要真正"按住到尾"，差一截松手不该判对；② 双押几乎不出现，希望更常见。

**改动（3 个常量 + 1 个测试）：**

| 常量 | 位置 | 改前 | 改后 |
|---|---|---|---|
| `holdReleaseMs` | `types.ts` | 180 | **135**（`goodMs` 的 1.5×，对齐 osu!mania ScoreV2） |
| `HOLD_TAIL_MIN_GAP_MS` | `types.ts` | 280 | **235**（与 `holdReleaseMs` 耦合，必须同步收缩） |
| `CHORD_CENTROID_SPREAD` | `lanes.ts` | 1500 | **800**（Hz） |

**依据**：

- 松手容差历史：初版 120ms（1.33×）实测偏严苛 → 放宽到 180ms（2×）→ 用户反馈
  "太松、差一截松手也判对，没有必须按住到尾的约束感" → 收到 1.5× 中间带。
  `HOLD_TAIL_MIN_GAP_MS` 与它是耦合的（`types.ts` 已注明），收紧容差必须同步收缩，
  否则"玩家还能在容差内松手，同轨下一个音符已经落下"。
- 双押门槛 1500Hz 只放行"底鼓 + 镲片"这类极端同格组合，双押几乎不出现；降到 800 后
  常见的"鼓点 + 人声/弦乐"同格组合也能拆成双押。`merged >= 2`（同格多起音）与
  `pickChordLanes` 的"不相邻、不跨手"约束仍在，不会生成打不出的谱面。
- 仅降阈值仍不够：双押依旧要求"两个音恰好同时响"，多数歌里几乎看不到。于是加
  **主动注入**（同日追加）：在**小节线（强拍）**把单个强音符拆成双押
  （`assignLanes` 的 `isInjectedChord`）。主轨走正常评分（反卡手/左右手均衡都生效），
  副轨由 `pickSecondaryLane` 挑——不相邻、跨手、且未被长按占用；找不到就退化成单押。

**测试**：新增 `generate.test.ts` 两条双押回归测试——① 同格双起音跨度 1000Hz 必须拆成
双押（阈值若被改回 1500 立刻变红）；② 小节线强拍的单起音必须被主动拆成双押（注入若被
去掉立刻变红）。74 → **76** 个全过；`tsc --noEmit` 干净。

## 2026-09-29 · 计分改满分制 + 评级档位

**需求**：总分固定 10000，平均摊到每个音符；命中得分、miss 不得分；按总分评级 P/S/A/B/C/D。

**改动**：

- `judge.ts` 的 `Scorer`：删掉旧的 combo 倍率计分，改成 `perNote = 10000 / 总音符数`，
  命中 `score += perNote`、miss 加零。判定档位（perfect/great/good）不再影响分值，
  只留在 `counts` 供结算页展示。连击照旧追踪（供显示），但**不再参与计分**。
- `judge.ts` 的 `gradeOf`：签名从 `(accuracy)` 改为 `(score)`，按总分分档
  P=10000、S=9000+、A=8000+、B=7000+、C=6000+、余下 D。
- `engine.ts` 的 `finish`：评级改传 `gradeOf(s.score)`（原来是 accuracy）。
- `render.ts`：HUD 分数补零宽度 7 → 5（满分 10000 只有 5 位）。
- `types.ts`：删掉已无引用的 `JUDGMENT_VALUE`。

**测试**：重写 `judge.test.ts` 的 Scorer 用例（全命中=10000、miss 扣分、连击不影响分数），
新增 `gradeOf` 分档用例。总数仍 **76** 个全过；`tsc --noEmit` 干净。
